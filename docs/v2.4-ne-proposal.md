## 0. Executive summary

1. **Our Zenodo products are a redistributed cadastre database.** Verified on
   real files: the `parcels` section is **75 % of a v2.3 KG JSON** (1.34 of
   1.79 MB) and its `vertex_heights` array is delta-coded lat/lon of *every*
   boundary vertex (46 568 vertices in KG 56604) → full parcel polygons +
   GNR ids are reconstructible from the JSON alone, in **v1, v2 and v2.3**.
   `building_footprints` (10–18 %) carries footprint vertices, `building_id`,
   and — in v2/v2.3 — **postal addresses** (296/499 buildings in 56604).
   The light GPKG additionally ships `parcels`, `buildings`,
   `parcel_outline_z` layers. The **full GPKG is clean** (schema verified from
   the writers: 31/32 segment props, no `dist_*`, no ids).
   `data/search_index.db` holds **3.26 M parcel rows keyed by parcel_id** —
   a lookup-by-number cadastre index.
2. **This contradicts the legal posture the rest of the ecosystem publishes**
   (siedler `/lizenzen`, `/api/licenses`): VTC tiles are CC BY 4.0 incl. §4
   sui-generis rights, *but* the self-imposed rule is "no cadastre database,
   ≤24 h cache, nothing queryable by Gst.-Nr./EZ/owner, only *what is
   here?*". We must adopt the same posture: **nothing cadastre-shaped is
   stored or published; parcel answers are computed per request from a live
   cadastre source and expire.**
3. **umfeld-at's NE cells are the right spatial unit** — with three
   measured fixes (§3): `bld_orient` leaks the exact axis of 72 % of single
   buildings, the k≥5 distributions fire on only 0.4 % of cells (useless at
   res 12), and 9.6 % of cells have `cov<0.9` / 916 cells have empty `lu`
   (verdict logic must treat them as *declared unknown*). Note: NE cells
   exist only as a **draft API for us** ("ask before building on it"); a
   production per-KG endpoint + umfeld-at's go-ahead are hard dependencies.
4. **Our contribution is the observed layer** (§4): per H3 res-12 cell —
   observed land-use mix in the same 9 groups, nDSM heights, tree count/
   height/crown cover, terrain, NDVI phenology, LiDAR change, and a
   `declared_vs_observed` verdict. ~10–12 B/cell deflated, ≈0.5 MB/KG.
   This turns two anonymous statistics layers into a wall-to-wall
   declared×observed land-use verification for Austria at 20 m.
5. **Reprocess in three stages, not one** (§6): (S1) stop the bleeding —
   today's code must stop writing cadastre sections (1 day); (S2) **strip
   in place** on Zenodo: DROP TABLE + VACUUM the light GPKGs, rewrite JSONs
   without the parcel sections, same-filename PUT — covers *all* 7 000+
   light/JSON files incl. v1 and the 569 KGs that have no full GPKG, ~2 TB
   down / ~1.5 TB up, no CPU, no Copernicus credits, ≈4–6 days fleet-wide;
   (S3) bump to **v2.4** (NE + observed layer) and let the *already running*
   v2 upgrade wave produce compliant products — only the 1 373 KGs already
   at v2.3 need a second pass. A single "v2.4 upgrade wave" alone would
   **not** clean Zenodo: the upgrade path never touches v1 `_light`/`_json`
   files and skips the 569 v1-only KGs (verified `v2_upgrade_eligible`).

## 3. Assessment of umfeld-at's NE proposal (measured on all 51 750 Kohlschwarz cells)

**Adopt.** Totals are internally consistent (Σland 1 584.8 ha; wald 916 /
gruen 581 / geb 8.0 ha; Σbld_cover = Σgeb; 581 buildings). H3 res 12 is
the right key: nests to 11/10/9, no geometry exchange, deterministic.

Fixes to agree before baking:

1. **`bld_orient` is a per-object attribute.** 419 cells have `bld_n==1`
   and all 419 report coherence 1.0 → the exact 1° axis of one footprint
   at a ~20 m location, for 72 % of the KG's buildings. Emit `bld_orient`
   (and `bld_p50`) only when `bld_n ≥ k`. Our observed layer can supply
   roof orientation from LiDAR instead (our object, no issue).
2. **Single-footprint area leak.** 12 cells have no `geb` in any neighbour
   → `bld_cover·307 m²` is that footprint's exact area; for the rest it is
   recoverable by summing `geb` over the 837 `bld_n==0` spill cells.
   Mitigation: quantise `bld_cover` to 1/255 at res 12 (like `lu`), keep
   1e-4 precision only from res 11 up. Tolerable either way (LiDAR roofs
   give the same number), but say so in the spec.
3. **k≥5 distributions are dead at res 12**: only 213/51 750 cells (0.4 %)
   reach `n_parc ≥ 5`; `bld_p50` appears in 0 cells; `n_parc == 1` in
   32 427 cells. Move `parc_p10/50/90`, `ez_n`, `parc_per_ez`, `bld_p50`
   to **res 10** (≈15 000 m², k satisfied almost everywhere) and drop them
   from res 12. Saves bytes and makes the k-rule meaningful.
4. **Coverage holes**: 4 975 cells (9.6 %) `cov < 0.9`, 916 cells empty
   `lu`, 534 cells `cov > 1.05` (max 2.0, tile-overlap double count).
   Need `cov` clamped/normalised server-side and a documented rule:
   `cov < 0.9 → declared = unknown` (no verdict).
5. **Resolution**: stay at res 12 for `lu`/`bld_cover`. Res 13 (44 m²)
   would let footprint shapes be re-traced at ~7 m — exactly the per-object
   reconstruction we are removing.
6. **Transport**: `kohlschwarz_ne.json.gz` is served *uncompressed*
   (7.29 MB); the production endpoint must gzip (~350 KB) and send an ETag.
   Prefer the packed binary (`ne_cells.py:pack`, 233 KB) with a versioned
   header `algo, epoch, h3_res, k, digest`.
7. **Production endpoint**: `GET /k/api/v1/ne/<kg_code>` for all 8 440 KGs
   (incl. split blocks → parent code), carrying `algo`, `epoch`, `digest`,
   `notice`. 8 440 × 350 KB ≈ 3 GB total fleet traffic — negligible.
8. **Status**: draft, "one client, ask before building on it". We need
   umfeld-at's explicit OK that baking NE cells into CC BY 4.0 Zenodo
   products (first publication of these cells anywhere) is intended.

## 4. Our contribution — the observed layer (`obs`)

Per res-12 cell, from our own rasters/vectors (no cadastre input):

| Field | Source | Enc. |
|---|---|---|
| `obs_lu{geb,bau,acker,gruen,wald,wasser,verkehr,alpen,sonst}` | `segment_type` 1 m → 9 NE groups (roof→geb; road/parking/bridge→verkehr; tree/forest→wald; grass/hedge/shrub/garden/orchard/vineyard→gruen; crop→acker; water→wasser; rock/bare→alpen or sonst by elevation; construction/excavation/fill→bau) | 1/255 |
| `obs_bld_cover` | roof pixels / cell | 1/255 |
| `h_mean, h_p90, h_max` | nDSM | dm, u16 |
| `tree_n, tree_h_max, crown_frac` | `tree_apices`, `tree_crowns` | u8/dm/1/255 |
| `elev_mean, slope_mean, aspect_dom` | DTM / terrain_coarse | m, °, 8-sector |
| `ndvi_mean, ndvi_amp, ndvi_phase` | S2 harmonics | 1/255, 1/255, 12 bins |
| `dh_mean, flight_years` | multi-date ALS (full GPKG only; null in upgrade-from-light) | dm |
| `dvso` | verdict, 1 byte: `consistent, forest_loss, forest_gain, sealed_undeclared, building_undeclared, green_undeclared, unknown` | u8 |

Verdict thresholds (prototype, to tune on 20 KGs): declared dominant group
≥ 0.5 and observed dominant group ≥ 0.5 of cell; `forest_loss` =
declared wald ≥ 0.6 ∧ obs wald < 0.25; `building_undeclared` =
obs_bld_cover ≥ 0.15 ∧ declared geb+bau < 0.03; `sealed_undeclared` =
obs verkehr+geb ≥ 0.5 ∧ declared gruen+acker+wald ≥ 0.7; `unknown` when
`cov < 0.9` or cell outside our tile union.

Cost (measured): `h3.latlng_to_cell` 0.54 µs/call → labelling the 1 m grid
of a 16 km² KG ≈ 9 s, at 5 m stride ≈ 0.4 s (recommended: compute cell id
per 5 m block, aggregate 1 m pixels per block — error < 1 % of cell area).
Size ≈ 24 B raw / 10–12 B deflated per cell → ≈ 0.5 MB/KG at res 12
(~50 k cells), res 11 ≈ 75 KB, res 10 ≈ 12 KB. Slot: inside
`build_light_gpkg_tiled`'s `v21_out` block (`austria_processor.py:5069–5150`)
where seg_type/height/labels/DTM are in memory; identical in fresh and
upgrade paths.

Product shape:
* **JSON** `ne` section: `{algo, epoch, h3_res:12, k, notice, digest,
  kg_composition_ha, obs_composition_ha, dvso_histogram_ha, cells_b64:
  <packed declared+observed records>}` plus a res-10 roll-up as readable
  JSON (≈460 cells) for humans/LLMs. Net JSON size: −1.5 MB (parcels +
  buildings) + ~0.6 MB → **smaller than today**.
* **Light GPKG** layer `ne_cells` (point at cell centroid, EPSG:4326,
  `cell_id` TEXT PK + declared + observed columns, res 12) and
  `ne_cells_r10` (hex polygons, res 10 roll-up incl. k-rule fields) — any
  GIS can read both; `layer_styles` for `dvso`.
* **Search index**: `kg_ne` (res-10 cells: kg_code, cell_id, lu/obs/dvso,
  heights) ≈ 3.9 M rows ≈ 300 MB, R-tree by centroid → bbox queries;
  `kg` gains `ne_epoch, ne_cells_total, dvso_*_ha`.

Offer the observed records back to umfeld-at (same key, same packing) so
both services serve both layers; our Zenodo products carry the frozen
pair with `epoch`.

## 5. `/k` functions — fresh logic

Design rule replaces "everything answers from `search_index.db`" for
parcel questions: **parcel-keyed answers are computed per request from a
live cadastre provider × our baked observed data, cached ≤ 24 h, never
persisted, every answer carries `notice`.** Point/bbox/cell questions
answer from the index (NE + observed, no parcel data).

* `cadastre_provider.py` — interface `parcels_at(point|bbox) → geometries +
  NS split`, `footprints_in(bbox)`. Implementations: `UmfeldProvider`
  (today: `/k/api/v1/export/geojson` or a new point/bbox route) and later
  `BevdirectProvider` (0.02° cells). 24 h LRU on disk (`data/cad_live/`,
  size-capped), same TTL rule siedler publishes.
* `live_parcel.py` — zonal stats of one geometry over `kg_v2_store.grid25`
  (25 m heightfield/landcover), `kg_trees` (apices), `kg_ne` observed cells
  (area-weighted), optional light-GPKG raster read (GpkgCache) when a
  caller asks `?precise=1`.
* Endpoints (all `/k`, token): `GET /api/v1/here?lon=&lat=` (the parcel
  under a point: cadastre attrs + our observed profile), `GET
  /api/v1/parcels/bbox?bbox=` (≤ 0.02°², per-parcel observed profile,
  `complete` flag), `GET /api/v1/ne/cells?bbox=&res=10|11|12`, `GET
  /api/v1/ne/<kg>` (frozen declared+observed pair as baked), `GET
  /api/v1/kg/<code>/profile` (NE composition + dvso hectares; no cadastre
  relay). **Removed**: `/parcel/<id>`, `/parcel/<id>/detail`,
  `/parcels/batch` by id, `/parcels/landscape`, `/query/parcels`,
  `?parcels=1`, `footprint_id` anywhere, `building_footprint_match.py`,
  `backfill_parcel_top10.py`, `fix_frav_inflation.py`, cadastre relay
  routes (`/lookup`, `/cadastre/*` — clients call umfeld-at directly).
  No live consumer exists today (net_stats), so no dual-serve period is
  needed; siedler already does its own per-parcel join from the public
  25 m heightfield.
* `kg_buildings`: keep as anonymous LiDAR building points (heights,
  storeys, roof type) — drop `building_id/footprint_id/footprint_area_sqm`.
  `kg_trees`: drop `parcel_id`, key by `cell_id` (res 12). QA flags
  `parcel_top_tree` → re-keyed to `cell_top_tree` (same lon/lat match).
* Public tier unchanged; `/api/v1/landscape` may later expose `dvso`
  hectares per bbox (cell statistics, parcel-free).

6. `GET /k/api/v1/ne/<kg_code>` for all 8 440 parent KGs; gzip + ETag;
   binary (`pack`) with a header `{magic, fmt_ver, algo, epoch, source,
   h3_res, k, kg, cells_n, digest, notice}`; JSON variant for debugging.
7. Cells on KG borders appear in every KG they touch with a `kg_share`
   field; cell stats are KG-independent (we dedupe by `cell_id`).
8. `lu` group order fixed and versioned; the NS→group table ships with the
   `algo` id (`ne-cells-0`): any change = new algo id.
9. `epoch` = ISO month + `source ∈ {index-2026-03, bevdirect}`; products
   freeze the pair.
10. Publish `ne_cells` as an importable, pinned package (shapely + h3 v4)
    so that cells computed from a bevdirect in-memory fetch are
    bit-identical to the index epoch — needed once the `/k` cadastre
    export is discontinued (we then compute declared cells per KG
    ourselves and post digests, as `ne_compare.py` intends).
11. Observed layer round-trip: `POST /k/api/v1/ne/<kg>/obs` accepting our
    packed records (`obs-cells-0`, same cell_id, same 9-group order) so
    umfeld-at can serve declared + observed; `GET …/ne/<kg>?layers=lu,obs`.
12. Fixed attribution string + `notice` in every payload.

## 11. Transition plan (agreed direction)

1. umfeld-at builds §10 → production NE endpoint.
2. Meanwhile (independent of umfeld-at): **S1 + S2 now** — stop writing
   cadastre sections, strip the archive. Every week of delay adds ~1 000
   more cadastre-shaped files (6.3 fresh + 7.1 upgrade per hour).
3. S3 = v2.4 rewrite: NE + observed layer in JSON, light GPKG, `kg_ne`.
4. Interim cadastre source for model features / `new_buildings`: umfeld
   `/k` export, **with a 24 h TTL on `cadastre_cache/`** (posture rule),
   never persisted beyond the KG run.
5. When umfeld-at discontinues the `/k` cadastre export: switch
   `cadastre_provider` to **bevdirect-serve running locally on each peer**
   (VTC tiles → 0.02° cells in memory; a KG needs ~5–10 cells ≈ 2–3 s
   each; parcels + footprints + NS split suffice for `dist_building`,
   `dist_parcel_edge`, `new_buildings`, and — via the pinned `ne_cells`
   package — for declared cells of later epochs).
