## What 2.4 changes (processor, every peer)

* **No cadastre-shaped output.** `austria_processor.CADASTRE_PRODUCTS = False`:
  the light GPKG has no `parcels` / `buildings` / `parcel_outline_z`; the JSON
  has no `parcels` / `building_footprints` (and no parcel coverage %, no
  addresses); `cadastre_free: true` flag.  The cadastre export is still
  fetched from umfeld `/k` at run time as **model context only** (segment
  features, `new_buildings`), cached ≤ 24 h (`cadastre_cache/`).
* **NE cells** (`ne_h3.py`): at KG start the parent's frozen declared layer
  NEC1 is fetched (`ne_h3.fetch_declared`, source `umfeld` or `bevdirect`);
  in `build_light_gpkg_tiled`'s v2.1 block the observed layer is built from
  the stitched 1 m arrays + apex inventory + 5 m coarse terrain:
  NEO1 41 B/cell (lu mix, bld cover/n, nDSM heights, trees, NDVI, dh, flight
  years, verdict, elev, slope mean/p90, aspect, roughness, TRI, TPI, dtm
  change, Hansen loss year, phenology), NET1 4 B/tree (all apices ≥ 3 m), NEB1
  8 B/man-made object with observed height.  Product `<code>_ne.h3b`
  (manifest key `_ne_h3b`, version `v2.4`): JSON header + res-10 chunks,
  byte-shuffled + zlib-9.  JSON section `ne` = summary + digests.
* **Blocks** of a split KG carry the parent's full cell set (unseen cells =
  nodata, header `partial_cells: true`); the peer POSTs NEO1 to umfeld only
  for unsplit KGs — split parents are merged + posted by the primary.
* **Verification** (`v2_verify`): `cadastre_free_sections/flag/text`,
  `light_gpkg_cadastre_free` (fatal), `ne_h3b_valid`, `ne_declared_digest`,
  `ne_observed_digest`, `ne_cells_observed`, `ne_algo`.  Missing NE (umfeld
  not built yet) is NOT fatal: product labelled `v2.4-partial` with defect
  `ne_cells` (`product_repair.defects`) → re-upgraded later.
* **Upload order**: `light_gpkg_v2` → `ne_h3b` → `json_v2` → (`json`, fresh
  only).  Every 2.4 product record gets manifest `status: cf`.
* **Legacy clean-up — strictly after the 2.4 pair (+h3b) is verified and
  committed** (`remove_legacy_products`, re-checked against the manifest via
  `v2_products_complete`; subprocess first, parent sweep as fallback):
  1. v1 `_json` → stripped (`strip_cadastre_from_doc`) and re-PUT **in place**
     (same filename/bucket; record `status: stripped`, `prev_uploaded_at`
     keeps the original stamp — progress-rate counters must ignore it).
  2. v1 `_light_gpkg` → deposition DELETED, record kept with `status:
     removed`, `removed_at`, `size: 0` (every "committed?" test reads it as
     absent; the director audits these against the deposition API).
  Older `_json_v2` / `_light_gpkg_v2` are replaced in place by the upload.
* **The 569 v1-only parents** (no `_full_gpkg`) cannot be upgraded; they get
  a normal fresh 2.4 run (frontier peers) — the fresh run rewrites `_json`,
  writes `_light_gpkg_v2`; its legacy sweep removes the v1 `_light_gpkg`.

## Manifest record vocabulary (zenodo_client.Entry)

| status | meaning |
|---|---|
| (none) | written before 2.4 → **suspect** (may carry cadastre data) unless `_full_gpkg`/`_ne_h3b` |
| `cf` | written by 2.4+ code, cadastre-free |
| `stripped` | v1 `_json` re-PUT in place without cadastre sections |
| `removed` | deposition deleted on Zenodo; record kept for the audit (size 0) |

`ne_rollout.py` turns this into the `legacy:` / `ne:` lines of `/process.txt`
and `director/status.ne_rollout`; `python3 ne_rollout.py audit 20` verifies
removed records against Zenodo (`legacy_audit.json`; `REMOVED-BUT-PRESENT`
is loud and must be re-deleted).

## Director (peer_director) — 2.4-first wave

Config `director_config` keys (all live-editable through
`POST /api/v1/director/config`): `v24_first` (bool, default true while
`legacy.suspect_files > 0`), `v24_frontier_cap` (int, default 4 — frontiers
kept for the 569 fresh runs while the wave runs), `ne_source`
(`umfeld`|`bevdirect`, default `umfeld`), `ne_require_built` (default true).

1. **Candidates**: with `MANIFEST_VERSION = v2.4` every code with a committed
   `_full_gpkg` is stale → `_compute_v2_upgrade_candidates` ranks them.  Gate
   each candidate on **umfeld built** (`ne_rollout.ne_built_codes()`, parent
   code of blocks) when `ne_require_built`; rank: half-landed pairs → codes
   whose parent still has a suspect file → rest; smallest full GPKG first.
2. **Fill**: in `v24_first` mode `_v2_upgrade_fill` ignores the
   `fill_below_ready` gate, the cache-ready fresh whitelist is emptied (all
   cache-only peers upgrade), `max_cache_only_peers` = fleet size minus
   frontiers/reserve, `_max_parallel_frontiers` ≤ `v24_frontier_cap`.
3. **Start payload** carries `ne_source` (app.py writes the
   `data/austria_processor/ne_source` sidecar; `ne_h3.ne_source()` reads it on
   every fetch).  Switching fleet-wide = one config POST; peers follow at their
   next NE fetch.  For `bevdirect` the director first calls each peer's
   `POST /api/v1/admin/ne_tooling` (installs pinned `ne_cells` from the public
   repo + bevdirect-serve binary served by the primary at
   `GET /api/v1/admin/bevdirect_binary`) and only switches peers that report
   `bevdirect_ready().binary && package`.
4. **569 v1-only parents**: `_v24_legacy_requeue` keeps ≤ 30 of them in the
   priority queue via the canonical `POST /processing/queue {kgs, position:0,
   skip_processed:false, keep_products:true}` (tombstone keeps them past the
   GET prune; products stay live until the fresh run replaces them).
5. **Audit tick** (every 5 min): `ne_rollout.audit_removed(20)`; re-issue the
   delete for `present` verdicts; `ne_rollout.refresh_ne_manifest()`.
6. **Split parents**: once every block's `_ne_h3b` is committed, the primary
   downloads them (rate-limited, `NE_INGEST_MB_PER_H`, default 25), merges the
   NEO1 rows (per cell: the block that observed it), writes
   `data/ne/<parent>.h3b`, POSTs the merged NEO1 to umfeld.  Unsplit KGs'
   h3b are downloaded under the same budget (on-disk fast path for the index).
7. **Exit**: when `legacy.suspect_files == 0` the director logs
   `v24: archive cadastre-free` and `v24_first` auto-clears → normal fill.
